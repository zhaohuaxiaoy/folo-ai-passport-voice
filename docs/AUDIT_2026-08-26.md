## 1. 总体结论

### 1.1 死锁 — 固件无环形等待;companion 有 2 处真实"卡死"路径

- **固件**:全部 13 个锁/信号量/队列对象均带超时(见 §4.2),音频链路不存在"高优先级任务等低优先级释放"的持有链 —— `ble_worker` 等待的 NOTIFY_TX 由优先级 21 的 NimBLE host 任务给出,高于一切应用任务。**未发现环形等待,不存在死锁**。
- **真实风险是"超时型丢事件"而非死锁**:队列满后事件被静默丢弃(`app_events.c:32-37` 满即丢;`ble_audio.c:541-544` 满则丢),最坏后果是 `KEY_RELEASE` 被丢(录音停不下来)、`APPROVAL_REQUEST` 被丢(审批不显示,不可恢复)。见 §2 P2-1/P2-2。
- **companion 有 2 处真实挂死**:
  1. USB 模式 `_stdin_loop` 阻塞在 `input()` 上,设备断连后 relay 永不收束 → 串口不关、重连失败、进程退出挂死(P1-4);
  2. Windows key 注入在事件循环线程同步执行 `time.sleep(2.0)`,每按一次键冻结核心链路 2 秒,10 秒音频缓冲塞满后丢帧(P1-3)。

### 1.2 性能 — 固件音频主路径近最优;余量风险集中在 BLE 吞吐与 WiFi 拆片

- **固件音频主路径(采集→环→发送)已近最优**:零拷贝、BLE 分片纯指针切片。
- **BLE 吞吐余量仅 0-30ms**:每帧 3200B = 7 片(MTU 517),单片最坏 10-15ms(加密+2M PHY),整帧 70-105ms vs 100ms 采集周期;环恰容 1 块,无抖动吸收,发送慢于采集即丢帧(P1-4,NOT RUN 真机验证)。
- **WiFi 路径配置失效**:`CONFIG_ESP_WEBSOCKET_CLIENT_BUFFER_SIZE_TX/RX=4096` 是无效符号(实际生效 `CONFIG_WS_BUFFER_SIZE=1024`),3200B 音频帧被拆成 4 条 WS 消息,且一次 `send_bin` 持锁时间 ×4(P1-1)。
- **固件事件延迟最坏 ~100ms**:app_task 无事件时 `vTaskDelay` 睡到下一心跳,事件最坏延迟一个 TICK 周期(100ms)。不影响正确性,影响手感。
- **companion**:key 注入冻结事件循环(见 1.1);其余路径(asyncio + to_thread 桥接)无阻塞性性能问题。

### 1.3 内存 — 余量 60-70KB(BLE 模式);可回收点主要是配置失误而非设计

| 项 | 数值 |
|---|---|
| 堆(运行时) | ≈ **119KB**(`_heap_start=0x3fcb14c0` − DRAM 起点 `0x3fc80000` = 201,920B 静态,DRAM 总量 321,296B) |
| 应用静态(main/ BSS) | ≈ 14.6KB(事件队列 1.9KB + 音频环/chunk 6.4KB + BLE 缓冲 4.1KB + ws/mdns ~2.2KB) |
| LVGL 池 | 24KB(固定,`LV_MEM_POOL_EXPAND_SIZE=0`) |
| NimBLE MSYS 池 | 10,752B(12×256 + 24×320) |
| 任务栈(应用自有) | ≈ 29.5KB;+taskLVGL(7168B)+NimBLE host(4096B)≈ 40.8KB |
| 常驻合计(BLE 模式) | ≈ 77KB,**余量 60-70KB** |
| WiFi/USB 模式增量 | ≈ 20KB(ws_task+mdns_worker 8.2KB、usb_link 任务+缓冲 ~13.5KB、WiFi 栈) |

**可回收点(均非设计缺陷,是真机/配置项)**:
- MSYS 配置符号无效 → 实际 7,680B,注释意图 2,560B,**多占 ~5KB**(P1-2);
- 任务栈收窄:应用栈合计 ~29.5KB 是否富余需真机 `st` 高水位(NOT RUN);
- LVGL 24KB 池峰值未实测(init 后 `lv_mem_monitor`,NOT RUN)。

### 4.3 死锁分析结论

- **固件:无环形等待。** 所有等待均带超时;音频/事件链路上不存在"高优先级任务等低优先级任务释放"的持有链(ble_worker 等的 NOTIFY_TX 由 prio 21 的 host 任务给出,高于一切应用任务)。主要风险是**超时型丢事件**(P2-1/P2-2)而非死锁。
- **companion 挂死位置**(标注):
  1. `fre_app.py:624-625` `_shutdown` 的 `thread.join(timeout=5)` — 正常退出最多冻结 5s;relay 卡死时是唯一兜底,超时后 destroy 但进程可能残留。
  2. `relay.py:337-345` + GUI USB 模式 — relay 线程永挂 + 非 daemon 执行器线程阻塞 stdin → **进程退出挂死**(P1-4)。
  3. `relay.py:491-502` + `inject_win.py:123-125` — 冻结 asyncio 事件循环,表现为音频丢帧/转写中断(P1-3)。
  4. 做得对的:`_probe_worker`/`_test_asr_worker`/`_relay_worker` 全部 daemon 化;`poll()` 只 queue.get_nowait,轻量。
- **companion 资源泄漏**(标注):
  - 线程:USB 模式每次断连泄漏一个阻塞在 input() 的 ThreadPoolExecutor 线程(P1-4);探测线程 daemon 一次性。
  - fd/loop:GUI 每次重连泄漏一个未 close 的 asyncio loop(selector + self-pipe,~2 fd)(P2-3)。
  - 连接:断连路径清理总体扎实(run 的 finally + abort + `_closing` 多槽,有测试覆盖);真正漏的是 P1-4 场景下 run() 的 finally 不执行 → 串口不关。
  - 队列/内存:`_audio_q`/`_event_q`/结果队列有界,`session_stats`/`decisions` 截断 100,reassemble 缓冲有超限清空 — 设计良好。
  - asyncio 任务:run finally 里 cancel approval/time 任务、abort 全部会话,`close_up`/`abort` 里 cancel `_run_task`/`_results_task`,`StreamingASR.close` 里 cancel `_recv_task` — 覆盖完整。
  - PIL/托盘:图标由 icon 持有,`tray.stop()` 后释放;无泄漏。
- **companion 被静默吞掉的错误**(标注):`inject.py:48-54` CGEventPost 无权限静默(**最危险**,P1-5);`inject.py:136-139` 剪贴板恢复失败静默(P2-5);`relay.py:564-586` approval 任务异常静默(P2-4);`asr_client.py:74-78` 畸形服务端帧静默成空结果(P3);`serial_transport.py:321-322`/`ws_transport.py:141-142` 回调异常 pass(设计如此,连日志都没有);`fre_app.py:513-514/522-523/535-537` 托盘异常只 print(可接受)。

### 4.4 重点机制确认(结论性说明)

- **flush 方式**:SPI 异步 DMA + ISR 回调 `lv_disp_flush_ready`;swap_bytes 在 flush 回调内原地字节交换(LVGL 任务),buffer 在 DMA 完成前不复用,无竞态。单缓冲下渲染与传输串行。
- **锁路径**:仅 app_task 与 taskLVGL 竞争 lvgl_mux(递归互斥);无第三方任务直接调 LVGL API。I2C 总线驱动自带事务互斥,CW2017(每 1s)与 ES8311(仅 boot/格式切换)共享安全。
- **按钮上下文**:esp_timer 任务(prio 22),回调只投事件,零阻塞 — 符合契约。
- **GPIO 冲突**:SPI(1/8/9/20)、I2C(7/10)、I2S(2/3/4/5/6)、背光(21)、USB(18/19)、ADC(0)全部无重叠;UART0 TX(GPIO21)冲突已通过 USB-Serial-JTAG 规避。注意 GPIO8/9 为 C3 strapping 引脚(硬件已定型,仅提示)。
- **分区表**:factory 4MB + nvs 24KB + phy 4KB,固件 ~1.75MB,余量充足;nvs 24KB 存 bond + 设置够用。
